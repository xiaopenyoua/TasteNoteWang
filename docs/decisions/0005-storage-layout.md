# 0005. 存储布局

## 背景

需要同时满足：查询快、可导出、可迁移、崩溃不丢数据、用户能看懂。候选：

- A. 纯文件（每条菜谱一个 JSON）为事实源，DB 只做索引。
- B. 纯 DB，媒体文件另存，导出时临时拼装。
- C. DB 为事实源 + 每条菜谱一个文件夹 + 派生 `recipe.json`。

## 决定

采用 **C**：

1. Room 是运行时唯一事实源；UI 只读 Room Flow。
2. 媒体与快照按 `recipes/{recipeId}/` 组织；文件名固定、ASCII。
3. 每次保存菜谱后写 `recipe.json`（派生快照）；备份/迁移以它和媒体文件为载体。
4. DB 只存相对路径；写入 `.part` + rename 原子落盘。
5. 备份导出以 **DB 的记录列表** 为准，目录只提供媒体文件；避免孤儿目录进包。

## 理由

- A 的查询/关联/事务实现成本高，且容易与索引不一致。
- B 的导出需要跨表拼装，用户拿到的是"应用专用格式"，停更即变砖。
- C 兼顾运行时性能（SQLite）与数据主权（自包含文件夹 + JSON + Markdown）。

## 后果

- 正面：查询快；导出简单；崩溃最多留下 `.part`；换机可恢复。
- 负面：DB 与文件双写，存在短暂不一致窗口；已通过"先事务后快照、快照可重建"约束。
- 负面：同一媒体若未来跨菜谱复用会重复存储；当前规模可接受。
- 触发重审：引入多设备同步、内容寻址去重、或单库超过 10 万条。
