# 味记・王 市场调研报告

> **日期**：2026-10-30　**调研范围**：中文安卓手机/平板的「收藏—执行」型菜谱工具，重点为抖音/小红书内容导入、本地存储与厨房场景；不含 iOS 版本规划。
> **方法**：桌面研究——应用商店页面、官网、用户协议与 robots.txt 原文、GitHub 仓库、媒体报道与社区原帖；所有数字均为 2026-10-30 单日快照。**未做**：真机分享面板实测、用户访谈、律师咨询、竞品真机功能复核。
> **可信度声明**：**硬数据**＝可复现的商店/官网/协议原文（评分、价格、下载量、star 数、条款编号）；**（推断）**＝由多条弱证据合成的判断；**（未验证）**＝单一二手来源或本轮无法复现。无来源的数字一律删除，不采用「市场空间 X 亿」式无推导结论。商店评分与下载量每日漂移，仅作量级参考。

**阅读须知**

- 逐条证据、来源 URL 与未决问题见 [`2026-10-30-market-research-evidence.md`](2026-10-30-market-research-evidence.md)。
- 文中「实测」指**调研代理在 2026-10-30 发起的 HTTP 抓取**，不等于真机验证，也不代表本人已复核；平台结构随时变化。
- 本报告存在一处**尚未裁决的内部矛盾**：4.1 描述 L2 元数据可自动获取，5.1 又要求零抓取。这不是笔误，而是两条路线之争。
  **2026-10-30 更新**：产品所有者已裁决采用端侧解析 + 媒体下载 + 无水印源优先，见 [`ADR 0003`](../decisions/0003-media-import.md)。本报告第 5 节的红线清单因此部分失效，保留作为风险依据；开发时以 ADR 0003 为准。

## 1. 一页结论（TL;DR）

1. **发现已迁走，执行仍空白**：小红书 2024 年中 MAU 3.2 亿/DAU 1.2 亿（二手转述），下厨房官网 360 万菜谱、8045 万作品；用户不缺菜谱，缺的是「收藏→做过」的桥。
2. **国内四强高度同质**：下厨房、豆果、懒饭、香哈均为内容社区+广告/会员/电商，全部不支持抖音/小红书链接导入，平板端普遍是手机版拉伸或平行视界。
3. **海外已用真金白银验证**：ReciMe 美区 32.4 万评分（4.79）、Paprika $4.99 买断 5.4 万评分（4.90）；社交视频导入在 2026 年已是标配，且普遍放在付费层。
4. **空位明确**：同时做到「中文短视频导入 + 安卓手机/平板原生 + 纯本地无账号 + 买断」的产品不存在；Plum 最接近但英文、0 评分、无安卓。
5. **导入是产品命门且分层**：抖音 L2 元数据可自动获取（白名单爬虫 UA 返回 JSON-LD，实测有效），小红书不稳定（短链过期、300031/300015 风控）；MVP 必须定在 L2 并随时静默降级到 L1（链接+手填）。（注：此条与合规红线冲突，待 ADR 0001 裁决；裁决前按 L1 设计。）
6. **合规分水岭是「有没有解析/下载通道」**：有，风险等同已被判赔的去水印工具（武汉 20 万、上海 30 万、成都 2024 当庭，均为二手报道，未核对判决书）；没有，只是一个本地笔记应用。MVP 应做零抓取、零下载、零账号。
7. **商业走买断不走订阅**：¥30-68 一次性，导入/查看/烹饪永久免费，零广告；北极星指标是「7 日复做率」，不是收藏数。
8. **三个 P0 未解问题**：分享面板实际给到什么字段、本地缓存第三方视频是否被允许、解析链路月均失效几次——任一条为否，定位就要改。

## 2. 市场与用户

### 2.1 目标人群与规模信号

- **画像**：一二线 25-35 岁、女性为主（小红书女性约七成、95 后 50%、一二线 50%，2024 年中二手转述）；独居与两口之家场景在增长（推断）。核心动机是工作日晚餐、带饭、减脂、给孩子做，而非钻研厨艺。
- **规模信号**：小红书食品行业人群 1.5 亿+（千瓜 2025-11，未核对原文）；下厨房作品数为菜谱数 22 倍（80,452,555 / 3,601,611，官网 2026-10-30），说明「看教程—照着做—晒成品」是成熟行为。
- **关键校正**：内容消费规模 ≠ 工具付费规模。全拓数据称 89.1% 用户只装一款菜谱 App（年份未标，推断为 2020-2021），正面争夺「学做菜」入口获客成本极高。味记不新增做饭人口，只承接已在抖音/小红书完成「发现」的那批人。
- **供给侧过剩**：豆果官网自称 500 万菜谱、5000 万用户。公共菜谱库已无商业价值，护城河只能是「用户自己的收藏 + 可执行性 + 私有数据」。

### 2.2 核心场景

| 场景 | 频率 | 痛点强度 | 现有替代方案 |
|---|---|---|---|
| 刷到即收藏 | 每天数次 | 中 | 平台收藏夹、专辑分组 |
| 做饭前找菜 / 今天吃什么 | 每天 1-3 次 | 高 | 翻收藏夹、搜索、问人、点外卖 |
| 跟做视频教程 | 每次新菜 | 高 | 反复拖进度条、暂停截图、抄食材 |
| 双手有油/面粉、自动熄屏 | 每次做饭 5-30 次交互 | 高 | 语音助手、隔空手势（易熄屏）、喊家人 |
| 备菜与采购 | 每周 1-3 次 | 高 | 备忘录、脑中记、临时下楼买 |
| 份量换算（1-2 人） | 每次新菜 | 中高 | 在线换算器、估着放 |
| 复做同一道菜 | 每周 2-4 次 | 中 | 手账、备忘录、凭记忆 |
| 换机/内容下架后找回 | 不可预测 | 高 | 无（直接丢失） |

### 2.3 「收藏即吃灰」的根因拆解

社区原话已把结论说透：知乎 2019-10-28（16 赞）「收藏的菜谱，不曾开过锅」；V2EX 2026-08-27 帖（2,282 次点击、27 回复）开发者自述「为了找到某个几秒钟的片段，只能不断拖动进度条」。（样本非随机，仅作定性证据。）

根因是五段断链，而非「用户懒」：

1. **找不到**：收藏越多越搜不到，平台收藏夹无结构、搜索弱、只进不出。
2. **看不懂**：食材在开头字幕、用量在口播、比例在评论区；视频线性，做饭是来回确认。
3. **做不了**：缺调料缺工具、双手沾油碰不了屏、熄屏打断、份量不适配 1-2 人。
4. **接不上**：收藏不解决「今天吃什么」，也不生成采购清单。
5. **存不住**（平台侧）：抖音视频可被删除/设私密，小红书短链过期后只 307 回首页（调研代理 2024-12 样本于 2026-10-30 失效）。

结构性原因：收藏是低成本即时满足，做菜是高成本延迟满足；平台收藏夹只优化「存」，从不优化「取」与「做」。**因此把收藏数做成首页主视觉，等于奖励用户重复失败。**

### 3.4 市场空位：味记・王 的机会

三句话定位：**不做菜谱库、不做社区、不做信息流**；只回答一个问题——「我收藏的这份教程，今晚能不能照着做出来」。空位由四个条件交叉而成：中文短视频解析（海外无人做）+ 安卓手机/平板原生（Apple 精品工具全部缺席）+ 纯本地无账号（Recipe Keeper/AnyList 要求账号）+ 买断（国内全是订阅/广告）。

一句话介绍建议：**「把抖音、小红书里收藏的教程，变成今晚能照着做的一道菜。」**

## 4. 关键技术可行性

### 4.1 内容导入路径与降级策略（产品命门）

**三层分级，成本与风险差一个数量级：**

| 层级 | 能力 | 网络/风险 | 抖音 | 小红书 |
|---|---|---|---|---|
| L1 本地解析 | 从分享文案正则提取平台+作者+标题+短链 | 0 请求、几乎不会坏 | ✅ 可行 | ✅ 可行 |
| L2 元数据 | 抓页面拿标题/作者/封面/时长 | 灰（伪造 UA / 解析页面） | ✅ 白名单爬虫 UA 返回 JSON-LD，实测 2026-10-30 有效 | ⚠️ 不稳定，需登录态，匿名访问被 300031/300015 拦截 |
| L3 媒体 | 下载原视频、去水印 | 高（合规红线） | ❌ 不做 | ❌ 不做 |

**调研时的抓取记录（2026-10-30，非真机）**：抖音 `v.douyin.com` 短链一次 302 即暴露 19 位视频 ID，任意 UA 可读；普通 Chrome UA 只得到 72,914 字节空壳页，带签名详情 API 直接 403（Argus）；封面 URL 可直接 GET 落盘（12,367 字节 JPEG）。小红书 `xhslink.com` 旧链接只 307 回首页；笔记页数据仍在 `__INITIAL_STATE__`，但境外/匿名访问被风控。**这些手段平台随时可收紧，必须做成可插拔策略而非硬编码。**

**入口优先级（三条，均已确认系统可行）：**

1. **系统分享面板**：manifest 声明 5 个 filter（SEND text/plain、image/*、video/* + SEND_MULTIPLE image/*、video/*），`exported=true`。ShareReceiverActivity 在 200ms 内写 Room 草稿后立即 finish，抓取/抽帧全部交给 WorkManager。
2. **桌面快捷方式 / QS Tile 打开「粘贴即存」页**：进入即有焦点，可合法读剪贴板。
3. **应用内粘贴框**：接受整段分享文案，用 `https?://[^\s，。！、）】]+` 抽链接后按域名白名单路由。

**明确不可行的路径**：后台剪贴板监听（Android 10+ 系统封死，官方原文明确）；App Links 接管抖音/小红书域名（无法托管 assetlinks.json）；静默后台接收分享（系统不存在该通道）；Direct Share 置顶（可争取 long-lived share target，但抖音/小红书是否渲染该行需真机验证，不能当唯一入口）。

**字段不对等**：抖音可得标题、作者、封面、时长、发布时间、互动数；小红书可得标题、正文、标签、作者 ID、图片列表，无时长、无独立发布时间。所有元数据字段必须 nullable，UI 用「未获取/待补充」占位。

**快照策略（导入即拥有）**：落库写入标题、作者、封面文件、正文文本、平台 ID、来源 URL、导入时间、抓取状态（成功/降级/手填）。URL 只做溯源跳转，失效后页面仍展示快照并标注「原链接可能失效」。

**MVP 承诺收敛为**：一粘即收藏 + 快速回看 + 手填 3 个字段（菜名、份量、关键步骤）。OCR/ASR 自动结构化放 v2，进入「待确认」状态，食材/用量/时间三类字段高亮可编辑。**宁可少解析 5-8 个关键步骤，也不要生成看似完整实则错漏的菜谱。**

**已识别矛盾的处置**：本地优先 vs 云端 AI → AI 可选、默认关闭、端侧优先；一键收录 vs 平台无 API → 明示真实成功率与手填兜底；视频为主 vs 存储/版权 → 默认只存封面+链接；平板优先 vs 手机采集 → 未验证前不投重资源。

### 4.2 技术栈建议

**100% Kotlin + Jetpack Compose + Material3 adaptive**，不选 Flutter（分享接收、MediaStore、Media3 全要写平台通道，还要背 Impeller 包体与 16KB 合规成本），第一版不引入 KMP/iOS（领域层放纯 Kotlin `:core` 保留退路）。

- **数据**：Room 3.0.3（KSP）为单一事实源，六张表 Recipe / Ingredient / Step / Media / Source / CookLog；UI 只 collect 本地 Flow。
- **播放**：Media3 ExoPlayer（变速、±10s、进度记忆、画中画、keepScreenOn），不用 VideoView。
- **后台**：WorkManager 唯一队列（enqueueUniqueWork + KEEP + 指数退避），不为同步常驻 Service。
- **搜索**：MVP 用 LIKE + 标签，数据量上来再上 FTS/trigram；中文分词不要一开始就设计复杂架构。
- **平台硬约束**：Play 2026-08-31 起新应用/更新必须 target API 36；target 36 起 edge-to-edge 不可退出、sw≥600dp 忽略屏幕方向；API 37 连 opt-out 都移除，且局域网访问变强制运行时权限；2027-02-01 起 16KB 页要求（纯 Kotlin 零成本合规）。
- **权限最小化**：Photo Picker、按需 READ_MEDIA_IMAGES、可选 CAMERA、前台剪贴板；**不要** READ_PHONE_STATE、QUERY_ALL_PACKAGES、后台定位、无障碍服务。

### 4.3 存储与媒体管理（先立规矩）

**第一条规矩：一条食谱 = 一个文件夹。** `recipes/{recipeId}/` 下放 `recipe.json`（结构化的唯一事实）、`cover.webp`、`steps/step-NN.webp`、`source.json`（平台/作者/原链接/导入时间/抓取状态）、可选 `transcript.vtt`。导出＝打包目录，导入＝读目录。这样既不锁死用户，也为将来同步/自托管留好路。

| 数据 | 存放位置 | 理由 |
|---|---|---|
| Room DB、设置、缩略图 | 内部 files/db | 启动必需、体量小 |
| 用户导入的原始视频（可选） | MediaStore `Movies/味记王` | 卸载不删，但归属丢失，需重关联 |
| 导出包 | SAF 用户选定目录 | 免权限、卸载不删，是无云端时最便宜的保险 |
| Auto Backup | 仅 DB + 缩略图，压到 20MB 内 | 25MB 硬上限，超限完全不上传 |

**存储增长必须算公式，不能拍脑袋**：单条体积 = 码率 × 时长，5 分钟 1080p 按 2-4 Mbps 计约 75-150 MB（估算，需实测）。结论：默认不缓存原视频，只存封面（480×270 WebP，`getScaledFrameAtTime` 取 1s 处）+ 关键帧 + 文本；用户可逐条选择缓存。图片统一 WebP q80、长边 1600px。

**备份三件套（设置页一级入口）**：① Auto Backup 只保 DB；② 一键导出 zip 到 SAF；③ 额外导出人类可读 Markdown/PDF，防止应用停更导致数据变砖。

**同步**：v1 零账号；可选 WebDAV 全量同步（文件级 mtime + Last-Write-Wins 即可，不自研 CRDT）；Android 17 连 NAS 需 ACCESS_LOCAL_NETWORK，错误提示要区分「网络不通」与「权限被拒」。

### 4.4 平板适配

**平板是厨房里的第二块屏，不是放大版手机。** 真实摆放是支架横屏、距离 50-100cm、需要大字与常亮。

- 宽度 ≥600dp 强制双栏：NavigationRail + ListDetailPaneScaffold；展开态详情再分「视频 | 步骤」。
- 烹饪模式：字号 ≥18sp、当前步骤高亮、其余变暗、多计时器、屏幕常亮、防油手大按钮（≥64dp）、音量键翻步、语音念步骤。
- 折叠屏半开：上半播放、下半步骤。
- 预览覆盖 1024×640dp、1280×800dp；MVP 锁定大屏 Tier 2（三尺寸可用、外接键盘可搜索），烹饪模式作为 Tier 1 差异点。
- **禁止锁定竖屏**——这是合规项不是优化项。
- 厨房人因（湿手/油手/0.5-1.5m/戴手套）尚未量化，需真实厨房 3 次可用性测试验证误触率。

## 5. 合规与风险

### 5.1 红线清单（照抄判决书，一条都不做）

- 不去水印、不绕过下载限制、不批量下载、不改 MD5、不导出评论。
- 不内置任何抖音/小红书接口调用、链接解析、视频下载；连「应用内深度链接跳抖音」也被抖音协议 5.3(4) 点名，退化为普通 https 交系统浏览器。
- 不自建抓取库、不做站内搜索抓取、不做公开分享社区（小红书 robots.txt `User-agent: *` 为 `Disallow: /`，调研代理 2026-10-30 抓取）。
- 不申请无障碍服务、不做自动打开 App 抓取（Play 政策明令禁止自主规划执行动作，可致账号终止）。
- 不后台监听剪贴板（系统封死，且易被判违规）。
- 商店标题/副标题/截图/更新说明不出现「下载」「去水印」「无水印」「解析」「搬运」。
- 每条记录强制显示来源平台 + 作者 + 原链接（著作权法第 24 条署名要求；成都案论证核心是「割裂作品与创作者和平台的联系」）。
- 不做公开分享；导出不含任何第三方素材；默认仅个人离线使用。
- 零账号、零联网权限可行；首启同意隐私政策前不初始化任何 SDK。

## 6. 对产品设计的 10 条硬性启示

1. **首页是「今晚吃什么」三选一 + 「最近做过」**，不是收藏瀑布流；收藏入口降级为次要动作。
2. **导入必须是首屏主路径**：分享面板 + 粘贴页，3 步内完成，允许「先存后补」，离线可用。
3. **「做过」是一等数据模型**：日期、照片、评分、我的改动、几人份；每条显示「已收藏 N 天未做」做温和提醒。
4. **步骤卡是原子单位，不是播放器**：每步一屏、用量就地显示、字号 ≥18sp，并保留跳回原视频该秒数的双向链接。
5. **烹饪模式 = 常亮 + 大字 + 大按钮 + 音量键翻步 + 语音**；不要只做手势，油手/暗光/远距离识别率差。
6. **平板 sw≥600dp 强制双栏**，烹饪页左步骤右视频+计时；绝不用手机布局拉伸。
7. **食材结构化 + 一键采购清单**：可勾选、按超市分区、可脱离菜谱独立存在；显式标注需提前腌制/浸泡/解冻。
8. **份量是一等属性**：1-4 人滑杆联动所有用量（含调料）；「适量/少许」原样存下等于把问题丢回用户。
9. **「我的版本」层**：原版与「我的改法」并存，做完 10 秒记一句；用户第三次做关心的是「上次哪里不对」。
10. **数据主权与商业**：一条食谱=一个文件夹；导出 zip + Markdown/PDF 放一级入口；买断 ¥30-68、永不订阅、零广告，导入/查看/烹饪永久免费。
